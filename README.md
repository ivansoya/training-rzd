# YOLO Dataset Manager

Веб-приложение для загрузки, валидации и просмотра статистики датасетов в формате YOLO.

- **Бэкенд:** Python + Flask, разбит на **микросервисы** (датасеты, аугментация,
  обучение/инференс), общий код — в пакете `backend/common`.
- **Фронтенд:** TypeScript + React (Vite). Компоненты разложены по папкам
  разделов (`components/common|datasets|augment|train|inference`), стили — на
  общие и по разделам (`src/styles/*.css`).
- **Шлюз:** nginx (`frontend`) — единственный внешний порт (8080): отдаёт SPA и
  маршрутизирует `/api/*` к нужному сервису.

### Архитектура (микросервисы)

| Сервис | Контейнер | Отвечает за | Образ |
| ------ | --------- | ----------- | ----- |
| `db` | `yolo-db` | PostgreSQL (пользователи, проекты, датасеты, разметка); порт 127.0.0.1:5432 для дебага | postgres:16 |
| `mailpit` | `yolo-mailpit` | Ловит исходящую почту в деве (UI: localhost:8025) | mailpit |
| `auth` | `yolo-auth` | `/api/auth`, `/api/friends`, `/api/projects`, `/api/invitations`; миграции Alembic при старте | лёгкий + SQLAlchemy |
| `datasets` | `yolo-datasets` | `/api/datasets`, `/api/jobs`, `/api/tasks`, `/api/images`, `/api/video-tracks` (разметка видео) | лёгкий |
| `video-worker` | — | Готовит видео: таблица кадров, копии ступеней 1080p/720p/480p, нарезка на перегоны. Тот же образ, что `datasets`, другая команда | лёгкий |
| `augmentation` | `yolo-augmentation` | `/api/aug/*` (конфиги, превью, генерация) | albumentations |
| `training` | `yolo-training` | `/api/trainings` (+SSE), `/api/models`, `/api/devices`, `/api/inference`, `/api/videos` | torch/GPU |
| `autolabel` | `yolo-autolabel` | `/api/auto/*` — полуавтоматическая разметка SAM2 (кадры изображений и видео) | torch + SAM2 |
| `frontend` | `yolo-frontend` | SPA + nginx-шлюз | nginx |
| `tests` | `yolo-tests` | Прогон тестов и отчёт на :8090. Профиль `dev`, в бою не поднимается | playwright + pytest |

Все сервисы монтируют один именованный том `yolo-data` (`/app/data`). Состояние
фоновых задач (`_jobs`) тоже лежит на нём, поэтому задачу, созданную сервисом
аугментации, отдаёт сервис датасетов (`/api/jobs`). Создание аугментаций —
`POST /api/aug/generate`.

## Возможности

- **Новый главный сайт («Магистраль»):** после входа — страница «Проекты»
  (создание в модальном окне: название, код, описание, приглашение друзей с
  ролью), страница проекта (паспорт, статистика разметок, занятое место,
  участники с онлайн-статусом, датасеты, классы) и личный кабинет. Старое
  приложение (датасеты/аугментации/обучение/видео) вынесено на отдельный
  маршрут `/tools` за тем же входом и напрямую с новым сайтом не связано.
- **Пользователи и вход:** регистрация по почте с **подтверждением письмом**
  (ссылка на 24 ч; в деве письма ловит Mailpit — localhost:8025; для прода
  задайте `SMTP_*` в env auth-сервиса), вход по логину или почте (до
  подтверждения закрыт), пароль — в БД только хеш, сессии в httpOnly-cookie
  (30 дней, хранятся в PostgreSQL). Кабинет: профиль, смена пароля
  (сбрасывает остальные сессии), **друзья** (заявка → принятие; друзей зовут
  в проекты одним кликом) и **приглашения в проекты** (принять/отклонить).
  Роли в проекте: администратор / редактор / просмотр; приглашает только
  администратор. Онлайн-статус: активность младше 2 минут.
- **Полигональная разметка кадров:** кроме рамок объект размечается контуром
  (инструмент `P`). Контур замыкается кликом по своей первой точке или Enter,
  меньше трёх точек не замыкается; вершины тянутся, двойной клик по ребру
  ставит новую, Alt+клик убирает. **В одном объекте несколько контуров** —
  вагон, заслонённый стойкой, остаётся одним объектом: `⇧P` добавляет контур
  к выбранному, правая кнопка на соседнем — «Присоединить к выбранному»,
  «Убрать этот контур» убирает часть. Полуавтомат (SAM2) закрепляет то, чем
  вы рисуете: включён контур — все куски маски ложатся одним объектом.
  Подробности — «Полигоны и формат YOLO» ниже.
- **Схема БД** (проекты, датасеты, изображения, разметка, классы/суперклассы,
  друзья, приглашения + каскады удаления) — `backend/common/models.py`;
  миграции Alembic (`backend/auth_svc/migrations/`) применяются при старте
  auth-контейнера.
- **Дев-режим:** бэкенд в docker (`docker compose up -d --build`), фронтенд —
  `cd frontend && npm run dev` (vite на :5173 проксирует `/api` в nginx :8080).
- Загрузка датасета в виде `.zip` архива (кнопка в скрываемом боковом меню слева).
- Валидация архива на соответствие формату YOLO:
  - наличие `*.yaml` конфигурации с `names` / `nc`;
  - наличие папок `images` и `labels`;
  - проверка каждого файла разметки `.txt`: строка из 5 значений — бокс,
    нечётное число от 7 — контур; нормализованные координаты `[0,1]`,
    корректный id класса.
- Распаковка валидного архива в отдельную папку.
- Датасеты разделены на **«Загруженные»** и **«Аугментированные»**, которые бэкенд
  хранит в разных папках:
  - `backend/data/uploaded/<name>` — загруженные пользователем;
  - `backend/data/augmented/<name>` — создаются **только самим приложением**.
- Боковое меню сворачивается; удаление датасета — кнопкой `✕` напротив каждого.
- Статистика выбранного датасета справа.
- **Аугментации (albumentations):**
  - раздел «Настроить аугментации» с редактором конфигураций;
  - конфигурация — это набор аугментаций с полным набором параметров каждой
    (параметры извлекаются интроспекцией из установленной версии albumentations);
  - есть встроенная базовая конфигурация без аугментаций (изменить/удалить нельзя);
  - окно превью: выбранная конфигурация применяется к случайному изображению
    датасета (с отрисовкой bbox, которые корректно трансформируются вместе с
    картинкой);
  - конфигурации хранятся на сервере (`backend/data/configs.json`).
- **Несколько конфигураций за раз:** при создании аугментации можно выбрать
  сразу несколько конфигураций — каждая выполняется как отдельный полный проход
  по изображениям датасета (N конфигураций → N проходов). Файлы из разных
  проходов получают суффикс (`x.aug1.png`, `x.aug2.png`, …) и складываются в один
  датасет.
- **Выбор охвата:** аугментировать **все изображения** или **только train**.
- **Прогресс-бары:** при загрузке датасета показывается прогресс передачи архива
  (после 100% — статус «Передача архива на сервер…», т.к. данные ещё идут по
  сети) и прогресс распаковки; при генерации аугментаций — сколько изображений
  обработано. Длинные операции выполняются на сервере как фоновые задачи, а
  интерфейс опрашивает их статус (`GET /api/jobs/<id>`).
- **Статистика считается один раз** после распаковки (показывается отдельным
  статусом «Подсчёт статистики…» без прогресс-бара) и кэшируется в
  `<датасет>/.stats.json`. Поскольку датасеты в программе неизменяемы,
  последующие открытия статистики мгновенны.
- **Обучение YOLO-моделей** (раздел «🧠 Обучение моделей»):
  - запуск обучения на выбранном датасете (загруженном или аугментированном);
  - выбор версии модели из доступных на сервере; свои модели (`.pt`/`.yaml`)
    можно добавлять и удалять;
  - настройка гиперпараметров (epochs, imgsz, batch, lr0, optimizer, patience и
    др.) и **выбор устройства — CPU или GPU** (если запущен GPU-образ);
  - **все аугментации YOLO принудительно отключены** при обучении;
  - **реальное время через SSE:** сервер сам пушит обновления клиенту
    (Server-Sent Events, `GET /api/trainings/<id>/stream`) — фронтенд ничего не
    опрашивает. Обновляются статус, текущая эпоха, метрики по эпохам (mAP50,
    mAP50-95, precision, recall, losses), а также **прогресс по итерациям внутри
    эпохи** (текущий батч / всего, скорость it/s и текущие box/cls/dfl losses),
    как в консольной полосе YOLO. После батчей эпохи показывается **прогресс
    валидации** (`Валидация N/M`) — видно, чего приложение «ждёт» в паузе после
    эпохи. Прогресс собирается через штатные коллбэки ultralytics
    (`on_train_epoch_start` / `on_train_batch_end` / `on_val_batch_end`);
  - **история всех обучений** со статистикой; обучение можно остановить;
  - **веса** (`best.pt`) сохраняются на сервере, их можно скачать и удалить
    (или удалить обучение целиком). Всё хранится в `backend/data/trainings/` и
    переживает перезапуск;
  - каждое обучение выполняется в отдельном процессе, поэтому «Остановить» и
    «Удалить» немедленно завершают его (вместе с дочерними процессами).
- **Проверка моделей (инференс)** (раздел «Проверка моделей»):
  - **библиотека видео с каталогами (проектами):** видео загружаются в
    именованный каталог (`backend/data/videos/`, метаданные в `meta.json`) и
    группируются по нему в боковом списке. Загружать и **просматривать видео в
    плеере можно независимо от того, есть ли обученные модели** (плеер
    поддерживает перемотку через HTTP range);
  - загрузка видео сопровождается прогресс-баром передачи;
  - когда модель есть — выбираешь её и запускаешь инференс по уже загруженному
    видео: сервер прогоняет кадры, рисует детекции и кодирует результат в H.264
    (через ffmpeg). Результат проигрывается на странице **с пометкой, какой
    моделью он обработан**;
  - статистика: число кадров, детекций, кадров с детекциями, детекций на кадр и
    разбивка по классам со средней уверенностью;
  - у каждого видео — своя история проверок (каждая помечена моделью); видео и
    его проверки удаляются (удаление видео каскадно убирает его проверки).
- Приложение запоминает, **из какого датасета** и **какими конфигурациями**
  создана каждая аугментация. Сохраняются **сами значения** конфигураций
  (снимок параметров), поэтому запись не теряется, даже если исходные
  конфигурации потом удалить. Хранится также пользовательское отображаемое имя
  (`backend/data/augmented.json`). Все такие датасеты лежат в отдельной папке
  `backend/data/augmented/` и доступны для просмотра наравне с загруженными.

## Полигоны и формат YOLO

Объект-полигон хранится **одной строкой** `annotations` с `ann_type="polygon"`
и геометрией `{"parts": [[[x, y], …], …]}` в пикселях изображения. Частей
несколько нарочно: объект бывает разорван, и обводка обязана показывать то же,
что охватывает рамка. Отверстий среди частей нет — SAM2 отдаёт внешние контуры
(`RETR_EXTERNAL`), а формат, в который мы выгружаем, отверстий не знает.

На проводе полигон **всегда несёт и свою охватывающую рамку** в полях
`x/y/w/h`. Это не избыточность: по ней стоит подпись класса, по ней же считает
выгрузка боксами, и всё, что умеет только прямоугольники, продолжает работать,
не зная о контурах. Что перед ним, читатель узнаёт по полю `kind`.

### Чего формат YOLO не умеет

Строка YOLO-seg — это `class x1 y1 x2 y2 …`, **один контур на объект**.
Объекта из двух кусков формат выразить не может, и выбора здесь два: склеить
или разложить на два объекта. Разложить нельзя — один вагон, заслонённый
стойкой, стал бы двумя вагонами, и модель училась бы считать неправильно.

Поэтому при выгрузке части **склеиваются перемычкой**: от одного куска к
ближайшей точке другого и обратно тем же путём. Перемычка проходится дважды,
ширины не имеет и при растеризации маски площади не даёт — склейка меняет
запись фигуры, а не фигуру. Так же поступает и сам ultralytics, приводя
многочастную сегментацию COCO к своему формату. Проверяется числами:
площадь склеенного кольца равна сумме площадей частей
(`tests/unit/test_polygon.py`).

Отдельно там же выравнивается **направление обхода** колец. Склейка встречных
обходов вычитает площадь вместо сложения, и заливка выбила бы в объекте дыру
ровно там, где лежит вторая часть.

### Две выгрузки

Вид разметки выбирается в окне экспорта.

| Выгрузка | Полигон | Бокс |
|---|---|---|
| **Боксы** | сводится к охватывающей рамке | как был |
| **Сегментация** | строка контура | **пропускается**, счётчик в плане |

Бокс в сегментацию не идёт осознанно: прямоугольник, записанный контуром, учил
бы модель, что объекты прямоугольные, и человек об этом не узнал бы. Сколько
объектов пропущено и почему — видно в окне плана **до** выгрузки.

**Круг замкнут не до конца, и это названо вслух в интерфейсе:** сегментацию
платформа выгружает и втягивает обратно (`importer` читает обе формы строки),
но **не обучает** — в `training_svc` заведены только модели детекции.

### Где что лежит

| Файл | Что в нём |
|---|---|
| `backend/datasets_svc/polygon.py` | чистая геометрия: части, площадь, рамка, подрезка, склейка, строки YOLO |
| `backend/datasets_svc/shapes.py` | фигура на проводе: одна запись и один разбор для бокса и контура |
| `frontend/src/components/mag/polygon.ts` | правка на клиенте: вершины, части, замыкание контура |
| `frontend/src/components/mag/overlay.ts` | арифметика слоя разметки: экранные координаты, пороги якорей |

`polygon.py` и `polygon.ts` пересекаются в **одной** функции — `bounds`, — и
совпадать она обязана: редактор ставит подпись по той же рамке, по которой
сервер сводит полигон к боксу. Расхождение выглядело бы как «подпись съехала»,
а означало бы другой датасет. Это тот же осознанный дубль, что у `trackMath.ts`
/ `video_tracks.py`, только гораздо меньше: разбор и подрезку геометрии делает
один сервер, а попадание курсора считает браузер по элементам SVG — своя
проверка «точка внутри кольца» была бы первым, что разойдётся с картинкой.

### Как нарисована разметка

Разметка рисуется **одним SVG поверх кадра и вне его трансформа**, в экранных
пикселях. Прежде рамки и якоря лежали внутри масштабируемого слоя, а толщины
делились на масштаб: на зуме 12 рамка становилась 0.167 px, а якорь 0.83 px со
смещением в полпикселя — величины, которые браузер округляет каждую грань
по-своему. Слой подписей и слой полуавтомата ушли из трансформа раньше и по
той же причине; теперь ушло всё, и деления на `--z` в проекте не осталось.

Что показывать, решает **экранный размер объекта, а не зум**: меньше 44 px
якорей нет вовсе (в них не попасть, а закрыть собой объект они успевают),
44–90 px — только углы, больше — углы и середины. Вершины контура появляются,
когда среднее ребро на экране длиннее 12 px, иначе 64 точки сливаются в
сплошной ободок. Зона попадания — всегда 10 экранных пикселей, независимо от
того, что нарисовано. Пороги закрыты числами в `overlay.test.ts`.

Бокс и контур различаются на кадре раньше, чем разбираешь их форму. Обводка у
обоих сплошная — она описывает форму и обязана быть точной; но у контура вокруг
неё идёт **пунктирный габарит**: рамка по самым крайним точкам объекта, одна на
все его части. По ней видно занятое место, а у разорванного объекта — что
половины, разнесённые по кадру, принадлежат одному целому. Невыбранный объект держит тихую
заливку цвета класса — она говорит «объект вот тут» боковым зрением; выбранный
заливку отдаёт, под ним нужно видеть пиксели. Вершины контура — ромбы, тем же
знаком, что ключевые кадры в дорожках треков. Белой каймы у якорей и вершин
нет: на десяти пикселях она съедала половину знака и превращала цвет класса в
намёк. Наведение анимировано, `prefers-reduced-motion` уважается.

Правка контура:

| Жест | Что делает |
|---|---|
| `P` | новый контур; замкнуть — клик по первой точке (она подрастает навстречу) или `Enter` |
| `Alt` + движение | показывает, куда встанет вершина — **под курсором**, — и усами к концам грани, какое ребро при этом разойдётся |
| `Alt` + клик | ставит её туда. Место выбирает человек, промежуток кольца — геометрия |
| правая кнопка на вершине | убрать точку (не ниже трёх) |
| `⇧P` | следующий контур ляжет в выбранный объект |
| `Del` | убрать объект, а при включённых раздельных частях — выбранную часть |

**Замкнув контур, редактор всегда возвращается в «выбор»**, даже при
залипании: готовый контур почти никогда не готов с первого раза, следом идёт
правка, а не второй контур. Залипание осталось у рамки, где объекты
действительно рисуют подряд.

**Полуавтомат запоминается.** Он не режим, а привычка: включив его однажды, к
нему не возвращаются. Поэтому смена инструмента и `Esc` его **не сбрасывают** —
переход «рамка → контур» не стоит лишнего включения. В «выборе» он просто
ничего не делает: рисовать там нечем.

**Разметка видно и на превью.** В киноленте, на плитках таски и на плитках
датасета рамка рисуется прямоугольником, а контур — своими кольцами и более
плотной заливкой: на сотне пикселей форма сама по себе уже не читается, а «это
не рамка» читаться обязано. Слой один на все три места
(`frontend/src/components/mag/ShapeMini.tsx`) — три набора `<span>`-ов
разошлись бы при первой же правке.

**Вечных подсказок в интерфейсе редактора кадров нет.** Разметчик смотрит в
кадр часами, и текст, прочитанный в первый день, все остальные дни только
отнимает у кадра место. Вместо них — кнопка «справка», та же, что в разметчике
видео: она гасит экран, оставляя светиться органы управления, показывает
клавишу прямо на каждом и даёт полный список сочетаний. Список один на
подсветку и на панель (`HELP` в `AnnotationEditor.tsx`): держи их порознь — и
однажды подсказка начнёт врать про клавишу. Всплывашка осталась ровно одна, на
выключенной кнопке полуавтомата, и это не подсказка, а диагноз: почему на неё
нельзя нажать.

**Двигать контуры по умолчанию нельзя** — это включается тумблером в настройках
контура (⚙ рядом с инструментом). Контур правят по вершинам, а перенос целиком
нужен редко и случается легко: промахнулся мимо точки, повёл мышь — и вся
обводка уехала с объекта, к которому её подгоняли, и вернуть её нечем, кроме
как обвести заново.

Вторым тумблером, уже внутри первого, включаются **части по отдельности**: у
разорванного вагона половины лежат в разных местах кадра, и «подвинуть объект»
— не то же, что «подвинуть эту половину». Выделенная часть обводится поверх
общей линии, вершины чужих частей приглушаются.

Замер на живом стенде: линия 2 px и на вписанном кадре, и на ×7.08 — одна и
та же; якорь 10 px на любом масштабе; объект 24×22, занимающий на экране
22 px, якорей не показывает, а он же на ×7.08 (155 px) показывает восемь.
Проба проверяет 49 условий, включая жесты: подсказка `Alt` стоит под курсором,
а не на грани; без разрешения контур не двигается; `Alt` добавляет ровно одну
вершину; двигается только выделенная часть; `Del` уносит часть, а когда она
последняя — объект. Отдельно проверяются справка (вечных подсказок нет, органы
помечены, список не пуст) и превью (рамка и контур нарисованы разными фигурами
и различаются весом заливки, слой прозрачен и картинку не закрывает), а также
черновик контура (тёмной подложки нет, пунктир цвета класса) и память
полуавтомата. Снимки — в `tests/e2e/test-results/`.

**Проба ходит в собранный контейнер, а не в vite:
правку интерфейса перед ней надо пересобрать** (`docker compose build frontend`).

### Контуры в разметке видео

Ролик размечается контуром так же, как кадр: инструмент `P`, замыкание кликом
по первой точке. Контур ложится **одиночной разметкой своего кадра** и при
закрытии разметки переезжает в кадр таски контуром же, а не рамкой.

**Треком контур не становится, и это осознанная граница.** Трек считает
положение между ключевыми кадрами сам, а посчитать контур нечем: у колец
разной длины нет очевидного соответствия вершин, и «интерполяция» свелась бы к
подмене одной фигуры другой — молча и там, где проверить её уже нельзя.
Появится это тогда, когда появится способ сопоставлять точки, а не раньше.

Запрет держится **на сервере**, а не только в интерфейсе: `/tracks` и
`/keys/<n>` отказывают контуру с объяснением. Интерфейс прячет кнопку, но ручка
открыта всем, а без проверки контур доехал бы до подрезки рамки и получил бы
«Рамка слишком мала» — то есть отправил бы человека искать ошибку в рамке,
которой он не рисовал. В меню объекта пункт «Сделать треком» у контура остаётся
на месте, но недоступен, и подпись рядом говорит почему.

## Разметка видео

Видео в таске — не только источник нарезки. При загрузке ролика выбирается, что
с ним делать, и режим закрепляется навсегда.

**Нарезать на кадры.** Как раньше: выбираете участки на дорожке, из них
получаются отдельные изображения, они и размечаются.

**Размечать видео.** Ролик размечается покадрово, а изображений до закрытия
разметки не существует — есть номера кадров и боксы на них (`video_tracks`,
`video_annotations`). Кадр под разметку отдаёт сервер; браузерного плеера в
редакторе нет вовсе, потому что `currentTime` не даёт номера кадра. Быстрая
перемотка держится на прогреве окна кадров одним проходом декодера: подряд
идущие кадры примерно в восемьдесят раз дешевле одиночных.

В редакторе два инструмента рисования:

- **бокс** — живёт на одном кадре, как разметка обычного изображения;
- **трек-бокс** — объект, живущий во времени, от кадра появления до кадра,
  где его убрали. Между ключевыми кадрами положение считается линейно
  (интерполяцию можно выключить у трека). Участки, где объект заслонён,
  задаются отрезками: на кадре он показан прерывистой рамкой, а в датасет
  такие кадры не идут. У трека свой **шаг выгрузки** — каждый N-й кадр уходит
  в таску, ключевые всегда.

Время объектов живёт дорожками под кадром: видно, кто когда появляется, где
они пересекаются и где кто заслонён. Ключ переносится протяжкой ромба, края
жизни — протяжкой краёв, заслонение режется `Alt`+протяжкой; то же есть в меню
по правой кнопке.

### Как ролик доезжает до браузера

Кадр не приезжает картинкой. Браузер получает **перегон** — кусок видео в 120
кадров — и разжимает его сам через WebCodecs. На ролике 2688×1520 прогрев окна
±120 кадров картинками стоил около 120 МБ, вшестеро больше веса всего ролика.

Готовит перегоны отдельный контейнер — `video-worker`. Раньше нарезка жила
потоками внутри сервиса датасетов и делила с ним пул gunicorn, а этот пул
обслуживает ещё и список тасок, и кадры, и сохранение боксов. Восьми
одновременных нарезок хватало, чтобы проект перестал отвечать всем — включая
тех, кто видео вообще не открывал.

**Очередь.** Работы лежат в таблице `video_jobs` и берутся через
`FOR UPDATE SKIP LOCKED`. Очередь в базе, а не в памяти процесса, потому что
она обязана переживать перезапуск, быть видной всем процессам разом и помнить
отказ: без последнего битый ролик заводил новую нарезку на каждое движение
разметчика по таймлайну и добивал машину сам.

Порядок работ — обещание разметчику, а не украшение:

| Работа | Очередь | Что делает |
| --- | --- | --- |
| `index` | 10 | таблица кадров; без неё ролик не открыть |
| `chunk` | 20 | один перегон, на который смотрит живой человек |
| `strip` | 25 | кинолента под таймлайном |
| `variant` | 30 | полная копия ступени качества |
| `chunkset` | 40 | все перегоны ступени |

Пулов два, и они не смешиваются: быстрый берёт `index` и `chunk`, медленный —
остальное. Будь пул один, все воркеры однажды оказались бы заняты копиями, и
запрос перегона встал бы за ними.

**Ступени качества — это файлы.** Из оригинала фоном делаются полные копии
1080p, 720p и 480p (ниже не спускаемся: на 360 разметчик перестаёт различать
мелкие объекты). Копия пишется с опорным кадром ровно на границе каждого
перегона и без B-кадров — тогда перегон вырезается из неё перекладыванием
пакетов, без разжатия и сжатия заново. Перекодировать приходится только
«Исходное», и только когда его попросили. Пути к копиям и каталогам перегонов
лежат в `video_assets`: файл появляется фоновой работой, и наличие пути в базе
— это и есть признак, что она дошла до конца.

**Таблица кадров живёт в базе** (`task_videos.frame_index`), а не файлом рядом
с роликом, как раньше. Довод «девяносто тысяч чисел в строке БД не ищутся и не
соединяются» верен, но читалась она на каждый запрос перегона — с тома, с
разбором JSON и разворотом дельт. Теперь она разворачивается один раз на
процесс и живёт в кэше, а ключ кэша — отпечаток таблицы, поэтому подменённый
ролик не может получить чужие номера кадров.

**Неготовое — это `202`, а не ошибка.** Сервер не держит соединение, пока идёт
нарезка: он ставит работу в очередь и отвечает, что готовится и насколько.
Клиент показывает полосу и приходит снова. Отказ (`409`) клиент запоминает и
какое-то время не повторяет — по той же причине, по которой его помнит очередь.

**Полуавтомат работает по кадру источника.** SAM2 читает распакованный кадр с
общего тома, и распаковывается тот **всегда в разрешении оригинала**, какую бы
ступень качества сейчас ни показывали. Причина в координатах: канва редактора
считает клик в пикселях ролика и о ступени не знает. Пока кадр брали из
ближайшего готового перегона, модель получала 1280×720 и точку из 1920×1080 —
обводила то, что оказалось в двух третях пути к цели, и отвечала в пикселях,
которых редактор не знает.

Второй слой той же защиты — пространство объявляется, а не угадывается: клиент
присылает в `/api/auto/.../predict` поле `space` (размер, в котором он рисует),
сервер пересчитывает по нему подсказки и возвращает рамку с обводкой в нём же.
Совпало с кадром — пересчёт вырождается в тождество. Для будущей сегментации
это и есть главное: полигон считается по самой крупной картинке, какая есть.

**Закрытие разметки.** Разметка становится кадрами не при сдаче таски, а
отдельным действием — «Закрыть разметку» у ролика. Оно достаёт кадры плана и
превращает их в обычные кадры таски: дальше они правятся обычным редактором,
уходят в проект штатной сдачей и никем не переписываются. Это событие, а не
вечная синхронизация, поэтому закрыть повторно, пока прежние кадры на месте,
нельзя — сперва их надо убрать («Удалить кадры ролика»). Кадры, уже принятые в
датасет, эта уборка не трогает: они данные проекта. При закрытии таски ролик
удаляется, размеченные кадры остаются.

## Тесты

Тесты живут в отдельном сервисе и запускаются страницей на
**http://localhost:8090**. Сервис под профилем `dev` — в бою не поднимается:

```bash
docker compose --profile dev up -d tests          # GPU-машина
docker compose -f docker-compose.mac.yml --profile dev up -d tests   # Mac
```

Пять наборов, каждый запускается отдельно или все разом:

| Набор | Чем | Что проверяет |
|---|---|---|
| Единицы | pytest | интерполяция треков, план выгрузки, лестница качества, **геометрия полигонов и склейка перемычкой** — без базы и сервера |
| API живого бэкенда | pytest + requests | загрузка ролика, треки, сдача таски, кадры в проекте, **полигоны от редактора до архива** |
| Нагрузка | pytest + requests | отвечает ли API, пока воркер режет видео; отказ и повтор работ |
| Клиент | vitest | расчёт положения объекта в редакторе — тот же, что на сервере; **арифметика слоя разметки и правка контуров** |
| Сквозные | Playwright | браузер входит по ссылке из письма, открывает таску и размечает видео |

Тесты работают с тем же бэкендом и той же базой, что открыты в браузере: всё,
что они создают, помечено префиксом `test-` и стирается в начале и в конце
прогона. Тестовый ролик генерируется на месте (3 с, 10 к/с), в репозитории
бинарников нет.

Наборы идут по очереди, а не разом: API и сквозные делят базу и вперемешку
мешали бы друг другу.

### Смотреть, как идёт прогон

На странице видно и ход, и итог. Пока набор работает, вместо таблицы показан
живой хвост вывода — строка на тест с процентом, — а рядом счётчик пройденных
и полоса выполнения. Как только набор закончился, на его место встаёт разбор по
тестам: что прошло, что упало и с каким сообщением. Полный вывод команды всегда
доступен под «Вывод команды».

Тот же прогон можно вести из терминала — удобно, когда чинишь конкретный тест:

```bash
# все API-тесты, строка на тест
docker exec -it yolo-tests python3 -m pytest /work/tests/api -v

# только про сдачу таски: остановка на первом падении, вывод print на экран
docker exec -it yolo-tests python3 -m pytest /work/tests/api -v -k сдача -x -s

# посмотреть, какие тесты вообще есть
docker exec -it yolo-tests python3 -m pytest /work/tests/api --collect-only -q

# чистая логика (быстро, ничего не поднимает)
docker exec -it yolo-tests python3 -m pytest /work/tests/unit -v

# нагрузка: отвечает ли API, пока воркер режет видео
docker exec -it yolo-tests python3 -m pytest /work/tests/load -v

# клиент
docker exec -it yolo-tests bash -lc 'cd /work/frontend && npx vitest run'
# и он же в режиме слежения: пересчитывается на каждое сохранение файла
docker exec -it yolo-tests bash -lc 'cd /work/frontend && npx vitest'

# сквозные, с показом каждого шага браузера
docker exec -it yolo-tests bash -lc \
  'cd /work/tests/e2e && ./node_modules/.bin/playwright test --reporter=list'
```

Упавший сквозной тест оставляет снимок экрана и трассу в
`tests/e2e/test-results/`. Трасса открывается так:

```bash
docker exec -it yolo-tests bash -lc \
  'cd /work/tests/e2e && ./node_modules/.bin/playwright show-trace --host 0.0.0.0 --port 9323 test-results/*/trace.zip'
```

Правки в `tests/**` и `frontend/src/**` подхватываются сразу — эти каталоги
смонтированы в контейнер, пересобирать образ не нужно.

## Запуск через Docker (рекомендуется)

```bash
docker compose up --build
```

Откройте **http://localhost:8080** (единственный внешний порт — nginx-шлюз).
Поднимаются четыре контейнера: `yolo-frontend` (шлюз+SPA), `yolo-datasets`,
`yolo-augmentation`, `yolo-training`.

### Где хранятся данные

Все датасеты, конфигурации, обучения и метаданные хранятся в **именованном
Docker-томе** `yolo-data` (смонтирован в `/app/data`). Том лежит в файловой
системе ext4 внутри ВМ Docker, а **не** через bind mount на диск Windows. Это
важно для производительности: на Docker Desktop/Windows bind mount идёт через
медленный слой обмена файлами, из-за чего загрузчик данных при обучении не
успевает кормить GPU (видеокарта простаивает в ожидании картинок). Именованный
том даёт почти нативную скорость I/O.

Данные **переживают пересборку образов** (`docker compose up --build`) и
`docker compose down`. Стираются они только при `docker compose down -v`.

```bash
# посмотреть том
docker volume ls | grep yolo-data
# сделать бэкап в tar
docker run --rm -v training-rzd_yolo-data:/data -v "$PWD":/out alpine \
  tar czf /out/yolo-data-backup.tar.gz -C /data .
```

Остановить: `docker compose down` (данные остаются).

### Два композа: GPU и Mac

`docker-compose.yml` — основной, для машины с NVIDIA. Сервисы `training` и
`autolabel` собираются с CUDA-сборкой torch (cu121 и cu128) и резервируют все
GPU через `deploy.resources.reservations.devices`. Требования на хосте:

- NVIDIA GPU и свежий драйвер;
- [NVIDIA Container Toolkit](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/install-guide.html)
  (чтобы Docker мог отдать GPU контейнеру).

На странице «Обучение моделей» в поле **«Устройство»** появятся доступные GPU;
обучение с выбранным GPU идёт на сервере, в контейнере.

`docker-compose.mac.yml` — для разработки на Mac с Apple Silicon:

```bash
docker compose -f docker-compose.mac.yml up -d --build
```

Тот же набор сервисов, но всё считает процессор: torch ставится обычными
arm64-колёсами с PyPI, nvidia-резервации сняты, SAM2 работает с
`SAM2_DEVICE=cpu` и лёгким весом `sam2.1_hiera_tiny`. Устройство «GPU» в UI не
появится — список придёт пустым, запрос обучения на GPU отклоняется.

> Docker Desktop на macOS запускает контейнеры в Linux-VM **без доступа к
> Metal**: ни CUDA, ни MPS внутри контейнера не существует. Ускорить обучение
> на Apple GPU можно только запуском сервиса на самом хосте, вне докера.

Имя compose-проекта оба файла берут из каталога, поэтому тома у них общие
(`training-rzd_pg-data`, `training-rzd_yolo-data`) — база и датасеты те же.
Одновременно поднять оба нельзя: совпадают имена контейнеров и порт 8080.
Правки в наборе сервисов нужно вносить в оба файла.

> **Shared memory.** Обучение использует несколько процессов загрузки данных
> (DataLoader), которые обмениваются батчами через `/dev/shm`. По умолчанию в
> Docker он всего 64 МБ, из-за чего возникает ошибка
> `bus error ... insufficient shared memory (shm)`. В `docker-compose.yml` для
> бэкенда задан `shm_size: "2gb"` — этого достаточно для типовых конфигураций.
> Для очень больших `batch`/`imgsz` увеличьте значение. Изменение `shm_size`
> применяется при `docker compose up` (пересборка образа не нужна — контейнер
> просто пересоздаётся).

## Разработка на Mac: бэкенд в докере, фронтенд на лету

Рабочая связка: весь бэкенд поднят контейнерами, а фронтенд крутится на хосте
через vite — правка в редакторе видна в браузере сразу, без пересборки образа.

```bash
# 1. Бэкенд (первый раз собирается долго: torch и SAM2)
docker compose -f docker-compose.mac.yml up -d --build

# 2. Тесты — отдельно, по профилю dev
docker compose -f docker-compose.mac.yml --profile dev up -d tests

# 3. Фронтенд на хосте
cd frontend
npm install        # один раз
npm run dev
```

Что где открывается:

| Адрес | Что это |
| --- | --- |
| **http://localhost:5173** | **рабочий адрес** — фронтенд с горячей перезагрузкой |
| http://localhost:8080 | тот же сайт, но собранный в контейнере (без HMR) |
| http://localhost:8090 | тесты и отчёт |
| http://localhost:8025 | Mailpit — письма подтверждения |
| 127.0.0.1:5432 | PostgreSQL для psql и alembic autogenerate |

Vite сам проксирует `/api/*` на nginx контейнера (`vite.config.ts`), поэтому
фронтенд на 5173 работает с настоящим бэкендом, включая SSE обучения и стриминг
видео. Ссылки подтверждения почты ведут на 5173 — за это отвечает `APP_BASE_URL`
у сервиса `auth`.

### Что требует пересборки, а что нет

- **Фронтенд на 5173** — ничего: сохранили файл, увидели результат.
- **Питон-сервисы** (`auth`, `datasets`, `autolabel`, …) — код вшит в образ,
  поэтому после правки нужен `docker compose -f docker-compose.mac.yml up -d
  --build datasets` (или другой сервис). Перезапуска без сборки не хватит.
- **Воркер видео** (`yolo-video-worker`) делит образ с `datasets` — у обоих
  сервисов в компоузе задан один `image: yolo-datasets`, поэтому
  `up -d --build datasets video-worker` пересобирает его один раз и оба
  контейнера едут на одном коде. Наружу воркер ничего не отдаёт, поэтому «не
  работает» выглядит как ролик, который вечно готовится — смотреть надо
  `docker compose logs -f video-worker`.
- **`nginx.conf`** вшит в образ фронтенда: добавили маршрут `/api/*` — пересоберите
  `frontend`, иначе запросы будут уходить в никуда.
- **Тесты** (`tests/**`, `frontend/src/**`) монтируются в контейнер — правку видно
  сразу, пересборка не нужна.
- **Схема БД** — новая ревизия alembic применяется при старте `auth`, то есть
  на ближайшем `up -d auth`.

> Сквозные тесты ходят на `http://frontend` — в **собранный** контейнер, а не в
> vite. Проверяя правку интерфейса через них, сперва пересоберите `frontend`.

### Отдельные сервисы без докера

Каждый сервис можно поднять и руками из папки `backend` (общий пакет `common`
доступен по `PYTHONPATH`), но тогда придётся самому решать вопрос маршрутизации,
который иначе берёт на себя nginx:

```bash
cd backend
python -m venv .venv && source .venv/bin/activate
pip install -r datasets_svc/requirements.txt
DATA_DIR=./data PYTHONPATH=. \
  DATABASE_URL=postgresql+psycopg2://app:app@127.0.0.1:5432/app \
  python -m datasets_svc.app
```

## API

| Метод  | Путь                          | Описание                                         |
| ------ | ----------------------------- | ------------------------------------------------ |
| GET    | `/api/datasets`               | список датасетов (с полем `kind`)                |
| POST   | `/api/datasets`               | загрузка `.zip` (multipart `file`) → возвращает `{job_id}` |
| GET    | `/api/datasets/<kind>/<name>` | статистика датасета                              |
| DELETE | `/api/datasets/<kind>/<name>` | удаление датасета                                |
| POST   | `/api/datasets/augmented`     | создать аугментацию `{source, config_ids, display_name, scope}` → `{job_id}` |
| GET    | `/api/jobs/<id>`              | статус фоновой задачи (прогресс/результат)       |
| GET/POST/DELETE | `/api/models[/<id>]` | версии моделей (список / добавить `.pt`/`.yaml` / удалить) |
| GET/POST | `/api/trainings`            | список обучений / запустить обучение → `{id}`    |
| GET    | `/api/trainings/<id>`         | состояние обучения (метрики по эпохам)            |
| GET    | `/api/trainings/<id>/stream`  | SSE-поток: сервер пушит состояние (эпохи + итерации) |
| POST   | `/api/trainings/<id>/stop`    | остановить обучение                              |
| DELETE | `/api/trainings/<id>`         | удалить обучение вместе с весами                 |
| GET/DELETE | `/api/trainings/<id>/weights` | скачать / удалить веса `best.pt`            |
| GET    | `/api/videos`                 | список видео в библиотеке (с каталогом)           |
| GET    | `/api/videos/catalogs`        | список каталогов (проектов)                       |
| POST   | `/api/videos`                 | загрузить видео (multipart `file` + `catalog`) → запись |
| GET    | `/api/videos/<id>/file`       | отдать видео (range/перемотка) — для плеера       |
| DELETE | `/api/videos/<id>`            | удалить видео (каскадно удаляет его проверки)     |
| GET    | `/api/inference/models`       | обученные модели, доступные для инференса         |
| GET    | `/api/inference[?video_id=]`  | список проверок (опц. фильтр по видео)            |
| POST   | `/api/inference`              | запустить инференс `{video_id, model_run_id}` → `{id}` |
| GET/DELETE | `/api/inference/<id>`     | состояние проверки / удалить                      |
| GET    | `/api/inference/<id>/video`   | размеченное видео (H.264, поддержка перемотки)    |
| GET    | `/api/aug/transforms`         | реестр доступных аугментаций и их параметров     |
| GET    | `/api/aug/configs`            | список конфигураций                              |
| POST   | `/api/aug/configs`            | создать конфигурацию                            |
| PUT    | `/api/aug/configs/<id>`       | изменить конфигурацию                           |
| DELETE | `/api/aug/configs/<id>`       | удалить конфигурацию                            |
| POST   | `/api/aug/preview`            | превью `{source, transforms}` → base64 PNG       |

`kind` — это `uploaded` или `augmented`.
